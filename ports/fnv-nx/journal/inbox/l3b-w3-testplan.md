# l3b-w3 test plan: L3b tests onto recipe-built roots and boot.py test ELFs

Read: w1 census (6385fff6), the trunk's verify/RECIPE.md, recipe.py (link, units_of), boot.py, bootmachine.py (a2453fe9), toolchain/guest/{crt0.s,runtime.c}, toolchain/include/fnvnx/hostapi.h,
lift/rt/build.json of claude/fnv-l3b-lift-w2 (be36b59a), the tests below. Nothing built; this is the plan. The deleted tests (r9test, addrwrap, r9equal, r9report) are out of scope.

## The target shape (the same for every ELF test)
- **Roots.** (R1) `lift/rt` (L3a; native C/C++ with the plugins; build.json of w2 has `"link": null`). (R2) one test root per test family, `lift/test/<family>/build.json`, admitted with
  `cxx_origin {"lifted_by": "lift/tools/liftgen.py"-style generator, "pack": <external>}`: all its C++ units are outputs of a `generated` stage (the case table in, one lifted unit per case function
  out; keyed by content, so an unchanged case is a cache hit), plus its own tiny driver. (R3) the guest runtime/crt0 of `toolchain/guest` (L5/toolchain) gives the FNXG entry `entry(api)`.
- **Run.** `boot.py run --elf T.elf` with a driver inside the ELF: for each case read `case_N.in` (struct cpu, 536 bytes, plus memory pages) through `fs_open/fs_read`, place the pages with
  `map_fixed` at their x86 addresses, call the lifted entry, write `case_N.out` (cpu + written pages) with `fs_write`, `exit(0)`. The host python only prepares `.in` files under SDROOT and
  compares `.out` with the expectation: the verdict is outside the ELF, as boot.py wants ("the tool only reports").
- **Oracle (class 10)** is never the code under test: an exe dump under Wine 9.0, a cited text (SDM / ReactOS / MSVC EH tables), or an independent model (Unicorn x86 = QEMU running the exe's own bytes).
- **Doubles rule.** The test defines only its own names (driver, case table, `main`). Everything a lifted unit or an rt unit needs is the real definition below, or a named gap.

## Can the recipe link objects of two roots into one ELF today? NO. (machinery gap, owner L1)
`recipe.py` `Job.link(ws, objs)` links exactly `objs` = the units of ITS root (`units_of(rec, root, files)`); `link` takes only `script/output/flags`; there is no key naming another root's
objects. The workaround "copy rt's sources into the test root with a generator" does not work: gate rule cxx_origin says a root is either native (plugins required) or lifted (no tracked C++, no plugins), and
rt is native while the cases are lifted, so the two cannot share a root. Needed: `link.roots: [{"root": "ports/fnv-nx/lift/rt", "objects": "all"}]` (objects taken from that root's objects.json by sha256, a
declared input of the ld stage, so the key stays a content key, and `linkstrict`/`stub` see the union). Until it exists no ELF test below can be linked. The same gap blocks the product link (lifted pack + rt + platform).

## Per test
Common to the five instest-style tests (instest_extra, x87dyn, mmxtest; also chain): symbols the harness defines today = `fnvl_call` (STUBX redefinition of CALLX), `fnvl_dispatch`, `fnvl_raise`,
`fnvl_raise_av` (rt.S), `fnvl_trace`, `fnvl_world_stop/resume` (already gone), `memcpy/memset/memmove`, `fnvl_host_ticks_ns` (hostticks.c). Replacements: `fnvl_dispatch` -> rt/rt.c + G4; `fnvl_raise`,
`fnvl_raise_av` -> rt/seh.cc (real; needs `fnvl_os_unhandled` -> rt/unhandled.cc -> G1..G3 closure); `fnvl_call`: not a symbol of the product (CALLX(h) is `L_##h()`); a case whose text calls another entry gets
that callee's closure lifted into the same test root (chain's rule), a case with an indirect target goes through `fnvl_dispatch`, so the call event is the real call; `fnvl_trace`: G6; `memcpy..`: G5;
`fnvl_host_ticks_ns`: G1. The one-instruction harness `instest.build/Arm` (Unicorn driven from Python) goes away: Python only writes `.in`, reads `.out`.

1. **test/instest_extra.py** (synthetic integer/system encodings, ENC table; 365 lines). Root `lift/test/xinst`: generated stage = ENC rows -> one lifted function per encoding at its fake address (the generator patches
   the Image as `FImage` does; no exe bytes needed except the memory pages of the state). Expected: x86 side = Unicorn x86 oracle on the same bytes (independent model); `--tables`
   (generated-C substring checks vs hand-written SDM/ReactOS class table) is not a run: it becomes a pure python unit test of the generator (no toolchain, no ELF), expectations cited per row (SDM Vol 2 / KiTrap0D). Gaps: G1-G5, G8; two-root link.
2. **test/x87dyn.py** (4 cases: stack overflow / empty slot, masked answer). Expected values are hand-written constants from the SDM (real indefinite 0xFFFF C000.. + IE|SF in the status word), not
   computed by the lifter: keep them as cited constants (SDM Vol 1 8.5.1.1, rows quoted in the file header). Root `lift/test/x87dyn`: 4 generated functions (the generator picks the instruction from the exe with the same predicate; the
   exe is an external/SDROOT input), dynamic variant `x87='dyn'`. It reads TOP/ST/mem through struct cpu `.out`. Gaps: as common; no extra. Note: it uses QEMU-free expectations, so it needs no x86 oracle.
3. **test/mmxtest.py** (7 sequences x87<->MMX). Expected: computed from the SDM with `f2x80`; independent of the code under test (QEMU keeps the old exponent so is not used). Root `lift/test/mmx`: 7 generated sequence
   functions at fake addresses; same driver. `fpfacts.ASSUME.update(('I-FPMASK','I-FPSTICKY'))` in the test is an assumption injection: it must instead read the real fact (A-FPMASK is an open fact of L3b, 55 of 830 loads unproven today): until the fact exists the lifter's emission for these sequences is not a rule, report as gap (owner L3b).
4. **test/sehcodes.py** (fnvl_raise codes -> NTSTATUS rows, segment state). Today: drv.cpp + rt/seh.c + stubs.S (`memset/memcpy`) linked at 0xE0000000, Unicorn from python. Doubles: `fnvl_os_unhandled` (collides with
   rt/unhandled.c) and `fnvl_dispatch` (collides with rt/rt.c). Rule that removes the collision: the driver registers a real SEH frame on `fs:[0]` (a guest-level handler, `test-own` function: Windows semantics, an ordinary handler that
   copies the EXCEPTION_RECORD and CONTEXT pointers into driver globals), so `fnvl_raise` finds a handler and the unhandled hook is never reached; `fnvl_os_unhandled` is the real one from rt/unhandled.cc and is not called. `fnvl_dispatch`: real (rt.c + G4 table, which for this test holds only the handler). Expected rows (NTSTATUS, ExceptionAddress, NumberParameters, Context.Eip): hand-written from ReactOS KiTrap00/01/03/04/05/06/0D, KiRaiseAssertion (cited text; keep, add the file+function citation per row; rows 3/8/10/11 have no citation in the file today). Segment rows: SDM Vol 3 3.4.2 + the Win32 process selector set (0x23/0x1b/0x3b), cited. Gaps: G2 (`struct cpu*` slot read by `fnvl_raise`), G3, G4, G5, two-root link.
5. **bench/chain.py** (multi-function chains, 300 roots: x86 Unicorn on the real image vs lifted closure). Expected: Unicorn x86 running the exe's own bytes (independent model, trace = (entry, esp) per call, regs, every written byte).
   Root `lift/test/chain`: one root per batch of chains is too many: generated stage takes the chain list (root + closure from universe.tsv) and emits the closure's lifted units (a subset of the pack; same unit
   content as the pack, so cache hits against the pack's own objects, no second compile). Harness symbols: `fnvl_nobody`, `fnvl_os_unhandled`, `fnvl_raise`, `fnvl_raise_av`, `fnvl_raise_ud` (collide with rt/enter.c, unhandled.c, seh.cc -> use the real ones),
   `fnvl_trace`, `fnvl_trace_sw` (G6), `fnvl_enter` (G7), `memcpy memset memmove` (G5), `tab.S` (G4: generated, not a double). `bench/chrun.py` host gcc sites (rt + rcptab.c compiled for the host) go away: the host
   side of chain is the x86 oracle, no host build needed. Gaps: G4-G8; two-root link; performance: 300 chains x a boot run each (boot.py is Unicorn Python): measure before committing to it.
6. **bench/ehtest.py** (SEH frames, RtlUnwind, RaiseException, hand-assembled functions). The x86 side runs "the SAME algorithm as rt/seh.c" in Python (header lines 4-6): the oracle restates the code under test, so it is not
   class 10. This cannot be moved onto boot.py as is. Plan: lifted side -> same shape as test 4 (real rt/seh.cc, real handlers lifted from the hand-assembled functions via keystone bytes into a generated stage; expected = Windows behaviour).
   Oracle replacement (owner L3b, farm, Wine 9.0): the same functions assembled into a PE image, run under Wine 9.0 with a logging handler, trace dumped; or the cited MSVC/NT exception dispatch rules (ReactOS `RtlDispatchException`/`RtlUnwind`)
   written as expected traces by hand per scenario. Until then the test is a gap, not a test. Also: harness's service entries SVC_UNW/SVC_RAISE (fake addresses the Python OS answers) stand for `RtlUnwind`/`RaiseException`: real = platform exports (G3).
7. **test/dsl_emit_test.py** (the emitted DSL forms compile: `-fsyntax-only` on 300-function TUs, flags of instest). No run, no oracle: it is a build property. Root `lift/test/dslemit`: `generated` stage = shapes.tsv (exe-derived census, external) -> one unit per shape
   (or one per bucket, fixed names like the pack's 4096 buckets), compiled by recipe.py with lifted-root rules (no plugins), so "compiled N of N" = the build is green and the stat is `objects.json` units vs shapes (the generator also writes
   `emitted.tsv`/`bad.tsv`/`undef.tsv` as outputs; the `undef-assigned` pair count becomes a generated file the gate reads, not a print). `-fsyntax-only` and the direct g++ call (site dsl_emit_test.py:76) go away. No link, no boot, no oracle (the proof of each
   form is proof/certs, not this test). Gaps: none beyond the lifted-root build of a generated pack with fake base addresses; the `FNVL_EMIT=dsl` switch is a mode the generator must take as an argument, not env (owner L3b).
8. **proof/tests/test_fpexact.py** (gate_fpexact on synthetic objects: certificate check, rcp rule, float->int plugin rule, farm program refusal). These are unit tests of a GATE; no ELF, no boot. Fixtures (asm objects, small C++ with
   casts) become tracked fixture sources of a root `lift/proof/fixtures` built by recipe.py; the gate runs on its `objects.json` (L1 manifest `fnvnx-built/1`, per the handoff note, after w4's head), `fnvnx_f2i_check` is the recipe's 9th plugin (w4) instead of the host-g++ build at line 65,
   `aarch64-linux-gnu-as/g++` direct calls (lines 59, 74) go away. Problem to solve first (L1): fixtures that must be RED (a bare float cast) cannot live in a root that must be green: need a negative-fixture root class whose expected verdict is declared (red findings = test passes). `test_farm_program_refuses_other_cpu` runs tools/rcpcert.c compiled with host gcc (line 170): it is a host-side farm program (G10), compile via a `"target":"host"` root;
   its expected value (refusal on a non-reference CPU) is the program's cpuid check against the pinned reference (class 10: hardware cpuid on the farm host). Gaps: negative-fixture root, w4's plugin/manifest, G10.
