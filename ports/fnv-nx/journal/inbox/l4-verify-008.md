# L4 VERIFY 008: the deko3d boundary model of the boot machine (design decision, 2026-11-11)

Owner order (CLAUDE.md, late night): one render backend, deko3d; the boot machine's GPU is the L4 model of the deko3d
boundary (the dk* functions, the libnx calls the backend makes, the command buffers); shaders run from the build's DKSH;
an instruction the model does not cover makes the build red. Tests meet this boundary only in this one shared model.

## Decisions

D1. **The product backend runs in the boot machine, unchanged.** L6A's backend (render/d3d9/backend/nx, LP64, built by
    `verify/recipe.py` as a product root with its pinned compiler) is loaded by the boot machine as the host module image:
    an ELF64 AArch64 static PIE mapped above 4 GiB (outside the 32-bit guest space, so `addr32`/ILP32 are untouched).
    The guest's module-10 calls (`ext_call(10, fn, args, n)`, nxgpu4.h) enter the image's dispatch entry as emulated
    code, exactly as on the console. Same object bytes as the console; no host recompilation, no second backend.
    Argument: the order says "the emulator runs the same product backend as the console"; anything compiled for the
    host CPU would be a second backend.
D2. **The boundary is a closed symbol set, bound by rule.** At load, every undefined symbol of the host image must be one
    of: a dk* row of `dkabi.tsv` (fnv-nx-build `l6a/dkabi`, 67 functions at 071b497, regenerated by L6A from the pinned
    deko3d header), or a libnx row of the same table (the 7 libnx calls; L6A adds them as rows). Each is bound to the
    model service `FNVNX_EXT_DK = 12` (L1, claude/fnv-l1-contract-w12 hostapi.h), fn = row number. Any other undefined
    symbol fails the load naming it (newlib and libstdc++ are linked into the image: product code, run emulated).
    The same binding serves L6A's host-test ELFs (tests that link the real backend files): one model, no per-test double.
D3. **The model is deko3d's documented contract at the pinned commit.** `verify/bootdk.py` implements every bound row:
    device, memory blocks (CPU address in host-image space, GPU virtual address space of the model), command buffers
    (recorded into the memory given by `dkCmdBufAddMemory`; when it is full the model calls the maker's `cbAddMem`, as
    deko3d does), command lists, queues (submit executes lists in order), fences, swapchain and present (a frame record
    and, with --frames, the image), image/sampler descriptors at deko3d's struct sizes. Exact byte consumption of a
    command is not part of deko3d's contract; the points where `cbAddMem` fires are a model INPUT (failure-injection
    rule of the order), so a test can place them at any record boundary. References for tests: deko3d source/header at
    373bfd43d8b2 (mirrored to fnv-nx-build `tools/deko3d`), cited per function.
D4. **Shaders.** `dkShaderInitialize` takes the DKSH from the memory block. The model decodes its Maxwell (SM 5.3) code
    and runs it in an interpreter. Gate `dkcover` (L4, class 7 side): every instruction of every DKSH the build
    produces (backend shaders and the translated pack) decodes to a form the interpreter covers; one uncovered form is
    red, naming DKSH, offset and form. The encoding reference is the DKSH producer itself (uam of dekotools
    c15523cea963), the semantics reference is the decoder table it emits; no emulator code is used (ARCHITECTURE D18).
D5. **Rasterisation** follows the deko3d device flags the backend sets (DepthZeroToOne, OriginUpperLeft) and the GL
    rasterisation rules for those flags. Pixel equality with the console is not claimed (OWNER assumption 4: console
    behaviour until a run on it); the first-frame milestone is the present call with its frame record.

## Phases (each one worker task, in this order)

P1 census: the host image's undefined-symbol set (whole backend, at a commit) and the opcode census of every DKSH the
   build produces. Needs L6A's backend product root in the recipe.
P2 loader: ELF64 host image in bootmachine (map, relocate, bind by D2, module 10 -> image dispatch); tests on a recipe
   built LP64 test image.
P3 bootdk.py object model (D3) with the cbAddMem schedule input.
P4 DKSH decoder + gate `dkcover` (D4).
P5 interpreter + rasteriser (D4, D5).

The boot run does not wait for P2-P5 before WinMain: the guest reaches module 10 only at D3D9 device creation.

## Asked

- L1: confirm FNVNX_EXT_DK = 12 with fn = dkabi row number, and the host-image region above 4 GiB in the layout.

## Agreed with L6A and L1 (22:45Z)

- Boundary table: nx-agent claude/fnv-l6a-deko `render/d3d9/backend/dkabi.tsv` @08252f17, 74 rows (67 deko3d + 7 libnx:
  eventClear, eventClose, eventWait, nwindowGetDefault, viCloseDisplay, viGetDisplayVsyncEvent, viOpenDisplay);
  fn = 1-based ordinal of non-comment rows, fn 0 = pop the cbError queue. Module FNVNX_EXT_DK = 12 (L1 w12 @6766d18a).
- The model body is a recipe-built host library `libdkmodel` (L4): dkmodel_create/destroy/ext/last_error,
  dkmodel_inject(fn, ordinal, documented result), cbAddMem placement as an injection input; `verify/bootdk.py` embeds it
  (dkmodel_guest_ptr over guest and host-image memory, dkmodel_on_present). This refines D3 (Python only embeds).
- DKSH decoder tables: generated by L6A from uam's own pinned source as a hermetic recipe stage; L4's interpreter and
  gate `dkcover` consume them (D4).
- Time: no model clock. The vsync event is signalled at each 1/60 s boundary of the boot machine's monotonic timer;
  eventWait returns on signal or timeout with libnx's documented results.
- L6A's 12 harnesses (137 doubled symbols) become LP64 host-test images linking the real backend files (D1/D2).

## Owner order 22:50Z: OpenGL is the reference for deko3d (trunk CLAUDE.md d7fac9b50)

- `verify/bootgpu.py` with its GL library stays in the boot machine and produces the GL reference frames; the dk model
  (module 12, libdkmodel, DKSH interpreter) is built beside it.
- **D6, deko acceptance check (P6, after P5):** the same nxgpu command stream (same D3D9 front end, same scenes and game
  frames) is rendered through `bootgpu.py` (GL) and through the dk model; the frames are compared. A difference is a
  deko3d defect until a rule explains it. The check verifies the deko3d backend; it never selects code. The recorded
  stream is the input of both runs, so the comparison does not depend on two runs of the game being equal.
