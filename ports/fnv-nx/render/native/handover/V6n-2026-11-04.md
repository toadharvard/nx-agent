# V6n hand-over, 2026-11-04 (orchestrator session -> render machine)

V6n is the independent verifier of the native renderer under D14. It sees code and claims, not S6n's reasoning.
Its brief is in the J-0064 entry in `JOURNAL.md`:

* enumerate every (shader class, pass, permutation, vertex format, state set) the engine can emit;
* a Nine-on-softpipe oracle;
* render-state differential fuzzing;
* a shader parity harness for when the player's `shaderpackage*.sdp` arrive;
* `docs/RENDER_VERIFY.md`.

## What exists

There are two exploration scripts, WIP, under `render/verify/enum/`. They commit no decomp output.

* **`wip_pass_adds.py <decomp>/src`** lists every `ShaderPassList::Add` (FUN_00ba9ee0) call site: the enclosing
  `@fnv` function and the pass-id argument.
  - 435 sites: 320 literal (286 distinct ids), 115 computed.
  - The bare `Add(` pattern also matches unrelated calls; they show up as ids >= 0x10000000.
* **`wip_devtab.py <decomp>/src`** summarises developer tables written as `arr[i].f00 = "*.hlsl"`. It found
  ShadowLightShader VS @0x00b71bf0 (155 entries) and SpeedTreeFrond.

## Finding: the pass enum header may not match the code (unconfirmed, high impact)

The decomp's `eBSSMPassEnum` header (`src/bsshader/bsshader_shader_layout.h`, 756 values) seems not to match the
ids the FNV code uses. RENDER_NATIVE.md's figures (756 values, 667 live, FIRST_ALPHA_PASS=494, family ranges) are in
doubt.

* BloodSplatter emits `0x2f0 + flag` (752/753); the header has BLOOD_SPLATTER = 666/667.
* Lighting30 `UpdateLightingPassState` @0x00bbd880 uses `index = pass - 376` and special-cases 730-749. Its
  colour-write ranges run 377-481. The header puts the 3X passes at 306-409, an offset of 71.
* ShadowLightShader's per-pass arrays have 759 entries (0x2f7), not 756.
* 30 literal emitted ids fall in the header's "unused" range (683, 700, 718-751).

Likely an FO3-era header with blocks inserted for FNV. Next: anchor each family (grass, leaves, tile, imagespace)
by the id its own emitter uses, and rebuild the real numbering.

## How the decomp encodes the pass space

### Emission

The `Add` call sites above. Computed ids need local resolution: ternaries, `flag + const`, assignments to locals.

### Configuration: per-class global pass arrays indexed by pass id

* **SLS:** `DAT_011fdff8[759]` of `NiD3DPass*`, plus four per-pass int arrays:
  - `011fcc80` (flags; 2048 on skinned passes);
  - `011fc0a0`;
  - `011fb4c0`;
  - `011fa8e0`.
* **Lighting30:** local index table `DAT_01200ec0[112]`, with per-pass masks `01200a28` and `01200868`.
* **Setup functions** write
  `pass = DAT_x; pass->vertexShader = DAT_v; pass->pixelShader = DAT_p; GetState()->SetNodeValue(D3DRS, value)`.
  That gives each pass its VS/PS and static render states, e.g.:

  | D3DRS | 27 | 15 | 7 | 23 | 14 | 168 | 195 |
  |---|---|---|---|---|---|---|---|
  | state | blend | alpha test | z enable | z func | z write | colour write | depth bias |

* **Render-time overrides** must be listed separately: stencil and colour write in `blk_00b60000_o2.cpp` ~7455, and
  colour write by pass range in Lighting30.

### VS/PS to binary and defines

* **Loader loops:** `ShaderEntry* e = &tbl[OFF]; for (i < N) sprintf("SLS2%03i.vso", i); DAT_ARR[i] = ...`.
* **SLS VS arrays:**
  - `011fdd88` (SLS1, 31 entries);
  - `011fde04` (SLS1S, 22);
  - `011fde5c` (SLS2, 103).
* **SLS PS array:** `011fda48` (208 = 48 + 160), with `SLS2%03is%01i.pso` variants at index 152 and 70-73. The PS
  tables are in @0x00b74210.
* **Other table forms:**
  - brace init in lighting30shader.cpp ~2236;
  - `.source` / `.path` / `.pFile` / `shaderN[0]` / `ShaderDesc("...")` in tallgrass, nolighting, tile, sky, bolt,
    beam and vfog;
  - the imagespace table in `blk_00b80000_o2.cpp`.

  The plan is a generic per-function string-literal scan.

## Next steps, in order

1. **Enumerator** `render/verify/enum/pass_space.py`. Join emitted x configured into (pass id, class, VS/PS binary +
   defines, static render states, skin/VC flags). Output to `build/` only. Report declared / configured / emitted /
   reachable counts per family.
2. **Oracle host tool.**
   - Link S6c's `render/nine/host/{nine_d3d9,nine_present,nine_adapter,nine_guid}.c` and `gate/gate_winsys.c`
     against the host Nine libs. No gate_alloc or malloc wrap is needed.
   - `nx_direct3d_create9()` gives softpipe Nine. Read results back with GetRenderTargetData + LockRect.
   - Recreate the host Nine build with `render/nine/build.sh <work> <jobs> host`, then
     `NINE=<work> render/nine/gate/build.sh <out>`. That is about 453 steps.
3. **Target side:** GL 4.5 core on llvmpipe, through EGL surfaceless (see the S6n note) or OSMesa.
   - `libOSMesa.so.8` is a distro package, but its headers have to come from a Mesa source tree.
   - S6n's state translator and GL backend do not exist yet. Define a `v6n` adapter header for them, plus your own
     spec model and deliberate trap mutants, to show the fuzzer catches each trap.
4. **Fuzzer** with a minimiser and committed reproducers. `*.bin` is gitignored, so use another extension.
5. **Parity harness** with S6b's tools: `render/shaders/build.sh --tests` builds the SM1-3 assembler with CTAB lines,
   `sdp2dksh` (`--pack` / `--list` / `--ctab`) and uam. Then write docs/RENDER_VERIFY.md.
